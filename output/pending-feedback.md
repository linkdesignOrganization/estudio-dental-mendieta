### Feedback de: devops (Iteración 1 — Pre-QA Deploy)
- **Verificar un "fix de datos seed" en frontend-only requiere mirar DOS capas distintas, no solo el manifest.** El `manifest.json` solo lleva *assets crudos* descubiertos en build-time (paths de fotos/SVGs); los datos derivados (los 6 profesionales, la asignación doc→paciente) se generan client-side desde `ar-data.ts`, compilados en un **lazy chunk de JS** (no el `main-*.js`, que aquí eran solo 25KB de bootstrap). Para confirmar los nombres exactos hubo que (a) curl al manifest para los 15 paths de SVG, y (b) bajar TODOS los chunks referenciados y greparlos. El `main` casi nunca tiene los datos de feature: con el builder `application` de Angular están code-split. Regla: para verificar datos de un feature en el bundle desplegado, enumerar los `chunk-*.js` (del `index.html` + los que esos chunks referencian) y grepear el set completo, no solo `main`.
- **Los acentos se minifican a escapes `\xNN` en el bundle → `grep -F` de la cadena acentuada literal FALLA.** "Martín"/"Béccar"/"Acuña" aparecían como `Mart\xEDn`/`B\xE9ccar`/`Acu\xF1a`. Di un falso "MISSING" hasta que grepié el stem sin acento (`Aguilera`, `Varela`) o el escape (`\xED`). Regla: al verificar strings con tildes/ñ en un bundle minificado, grepear por el stem ASCII o por el patrón `\xNN`, nunca por el carácter UTF-8 crudo.
- **Para probar que un asset estático sirve de verdad (no SPA-fallback enmascarando un 404) hace falta un CONTROL NEGATIVO, no solo status+content-type.** Confirmé `image/svg+xml` en los 15 SVGs, pero el SWA con SPA fallback devuelve `200 text/html` para CUALQUIER ruta inexistente. Pedí explícitamente un path falso (`/imagenes/documentos/NOPE-99.svg`) → `200 text/html`: eso PRUEBA que el `image/svg+xml` de los reales es genuino. Sin el control negativo, "200 + content-type correcto" no descarta que el server esté inventando la respuesta. (Refuerza la nota previa de infra sobre fotos `/seed/fotos/...`.)
- **"El tab Documentos muestra thumbnails" NO se puede verificar abriendo un paciente cualquiera: por diseño del seed (UX-048) algunos pacientes no tienen documentos.** Abrí `pac-001` y vi "Sin documentos" (placeholder correcto, no bug) — casi lo reporto como fallo. Regla: cuando un dato está distribuido parcialmente (N docs sobre M pacientes, "algunos sin"), no asumir que el primer registro lo tiene; iterar hasta encontrar un caso positivo, y reconocer el empty-state controlado como esperado.
- **Verificación de render real de imagen = `img.complete && img.naturalWidth>0` vía Playwright, no el status HTTP del asset.** Un `<img>` puede apuntar a un SVG que sirve 200 pero romperse en el cliente (CSP `img-src`, MIME, parse). Comprobar `naturalWidth>0` en el DOM tras cargar el tab es la prueba de "thumbnail real, no roto" que pidió la tarea; el curl al asset es complementario, no suficiente.

### Feedback de: developer (Iteración 1 — Simplify + Security review del diff de Fundación)
- **Para auditar XSS de assets SVG nuevos, lo que decide el veredicto es el SINK de renderizado, no el contenido del SVG.** Un SVG servido por `<img [src]>` corre en contexto-imagen: el navegador desactiva todo scripting (ni `<script>` ni `onload` ejecutan), así que aunque el asset fuera malicioso el riesgo es nulo. El mismo SVG por `[innerHTML]`/`bypassSecurityTrustHtml` SÍ ejecutaría. Aquí confirmé los dos paths: thumbnails de documentos → `<img [src]="d.thumbnailPath">` (seguro), e `icon.component` → `[innerHTML]` pero alimentado SOLO de un allowlist interno (`PHOSPHOR_PATHS`), con el único valor dinámico (`size`) coaccionado a entero acotado, y los SVGs nuevos nunca llegan a ese componente. Regla: grepear `innerHTML|bypassSecurity|DomSanitizer` en `src/` y mapear si el dato NUEVO alcanza alguno de esos sinks; si solo va por `<img src>`/interpolación `{{ }}`, no hay vector aunque el grep "encuentre" un bypass preexistente fuera de scope.
- **Igual escanear los assets es barato y vale la pena como defensa en profundidad:** `grep -RIEli '<script|onload|onerror|onclick|javascript:|foreignObject|<a |xlink:href|<iframe|<use|data:text/html' <dir>` sobre los 15 SVGs (exit 1 = limpios) confirma que son vectores estáticos puros (rect/ellipse/line/text/gradient con `url(#frag)` local inerte). Documentar el exit-code del grep en el RETORNO da evidencia concreta.
- **Un refactor de "simplify" sobre un generador determinista debe preservar el ORDEN y NÚMERO de draws del PRNG, no solo el output de una corrida.** Extraer 3 bloques duplicados de construcción de documento en helpers `thumbFor`/`pushDoc` está bien SOLO si dentro de `pushDoc` la secuencia de `rng` (chance→pick(names)→int(fecha)) queda idéntica a la inline original; si se reordena o se agrega un draw condicional, se rompe el "reset fiel". Verifiqué leyendo el diff que el orden coincide. El `npm audit` (0 vulns) y `ng build --configuration production` (build_exit=0, 102 kB gz, sin budget exceeded) + `tsc --noEmit` (exit 0) son los gates que cierran; las warnings de `@import` de Sass son ruido preexistente aceptable.

### Feedback de: developer (Iteración 1 — corrección regresión seed PRNG)
- **Un draw del PRNG global protegido por un guard de longitud (`pool.length ? rng.pick(pool) : ''`) es una bomba de tiempo de regresión: cuando el pool pasa de vacío a poblado, ACTIVA un draw que antes no ocurría y DESPLAZA toda la secuencia downstream.** En FASE 4 `manifest.documentos` estaba `[]` → ese `rng.pick(pool)` nunca corría (3 draws/doc). En Iteración 1, al poblar los SVGs (REQ-058) el pool dejó de estar vacío → 4 draws/doc → presupuestos/facturas/movimientos cambiaron de valores (saldos, estados) aunque su CÓDIGO no se tocó. Regla: cualquier consumo del PRNG cuya *ejecución* dependa de datos variables (manifest, flags) rompe el determinismo cross-build. Lo cosmético/derivado de assets (thumbnails, avatars) debe usar un **PRNG separado con semilla propia** (`new Prng(SEED_ROOT ^ tag)`), nunca el rng global de la secuencia de negocio.
- **El diagnóstico inicial del PM ("el cambio de buildDocuments/profesionales desplazó la secuencia") era una hipótesis razonable pero FALSA; los datos la refutaron.** Comparar OLD-code vs NEW-code contra el MISMO manifest dio resultados byte-idénticos → el código no era la causa. La causa era el CAMBIO DE MANIFEST (`documentos: [] → 15 SVGs`). Regla: antes de "restaurar el orden de draws" del código, aislar la variable real corriendo el generador con cada combinación {código viejo/nuevo} × {input viejo/nuevo}. El smoke-test en node (esbuild local + `generateSeed`) lo confirma en segundos sin browser; ahí se ve que el verdadero disparador fue el input, no el código.
- **Verificar specs de FASE 4 contra el fix requiere servirlos LOCALMENTE: el `playwright.config.ts` apunta a la URL desplegada (Azure), que aún tiene el build viejo/roto.** Como el deploy lo hace el PM (paso 5d) y yo no debo deployar, serví el `dist` de producción con un mini server SPA-fallback (Node, con control de assets vs fallback a index.html) y un config temporal que extiende el base sobreescribiendo solo `baseURL: http://localhost:4399`. Los 98 tests (49×2 projects) pasaron contra mi build local. Regla: para validar un fix antes del deploy del PM, montar el build localmente + override de baseURL vía config que herede del original; limpiar el config y el server temporales al terminar (no dejar `playwright.local.config.ts` ni `_serve.tmp.mjs` en el repo).

### Feedback de: devops (Iteración 1 — re-deploy fix de regresión de seed, FASE 5)

Regla: si verificás el build localmente antes de commitear y hay un artefacto build-time tracked, revertí su churn de timestamp/hash y dejá que el CI lo regenere; el commit debe contener exactamente el fix + reportes, nada más.
- **El cambio de hash del bundle `main-*.js` en la respuesta del sitio es la prueba barata de que el fix está REALMENTE desplegado y no es caché del CDN.** Tras el push el sitio sirve `main-5CCD4VTD.js` (antes `main-GFYDB2WD.js`); como el contenido del bundle cambió, su hash de contenido cambia → si tras un deploy "success" el hash siguiera igual, sospecharía de un build que no incluyó el cambio o de caché. Verificarlo es un `curl -s "$SITE/" | grep -oE 'main-[A-Z0-9]+\.js'` y comparar contra el deploy previo (documentado en infrastructure-setup.md). Más fuerte que solo mirar `gh run ... success`.
